|---|---|
| 기간 | 2026-07-17부터 2026-07-22 |

## 시작한 이유

재무 질문은 같은 계정명이라도 회사, 보고기간, 연결 또는 별도, 보고서 종류, 정정공시 시점에 따라 다른 값을 가질 수 있습니다. 일반적인 문서 요약은 문맥을 설명할 수 있지만, 이런 조건을 매번 같은 규칙으로 적용하고 원문 근거까지 연결하는 데에는 별도의 데이터 계층이 필요하다고 봤어요.

그래서 질문 범위를 무한히 넓히지 않고 두 기업, 정해진 보고서, 표준 재무지표부터 고정했습니다. 목표는 “많이 대답하는 챗봇”보다 “답변 기준을 다시 확인할 수 있는 도구”였습니다.

## 개인 기여

주제 선정부터 구현과 검증까지 혼자 진행했습니다.

- 지원 범위와 하지 않을 일 결정
- OpenDART 수집, snapshot, manifest 계약 설계
- 재무 행과 공시 원문의 저장 구조 설계
- SQL 계산 경로와 pgvector 검색 경로 구현
- 근거 상태와 실패 상태 정의
- API와 화면 구현
- 테스트, 배포 확인, 공개 범위 점검

AI 코딩 도구를 사용했지만 사람 팀원에게 역할을 나누지는 않았습니다. AI의 제안은 구현 재료로 사용했고, 문제 정의와 수용 기준, 결과 확인은 프로젝트 소유자가 책임졌어요.

## 가장 어려웠던 문제

### 관찰

일부 2024년과 2025년 값이 0으로 보였습니다. 원문 데이터가 없는 것이 아니라 조회가 다른 행을 선택하고 있었어요.

### 문제 정의

동일한 계정명이 여러 재무제표에 존재할 수 있고, 정정공시는 같은 기간의 여러 revision을 남깁니다. 따라서 계정명 하나만으로 첫 번째 행을 선택하는 방식은 다음 불변식을 지키지 못했습니다.

- 요청 시점에 유효한 최신 revision일 것
- 지표의 의미에 맞는 재무제표일 것
- 회사, 기간, 보고서, CFS 또는 OFS 기준이 모두 맞을 것

### 선택

최신 유효 revision을 먼저 결정하고, 이후 지표별 재무제표 우선순위를 적용했습니다. 매출과 영업이익은 IS와 CIS, 자산과 부채는 BS, 영업활동현금흐름은 CF가 기준이 됩니다.

초기 동작과 최종 동작은 확인되지만, 당시 검토했던 다른 대안의 상세 목록은 보존되지 않았습니다. 공개 문서에서 그 과정을 새로 지어내지 않아요.

### 시행착오와 개선

1. 0으로 보이는 값과 OpenDART 원문을 대조했습니다.
2. 동일 계정명의 중복 행과 revision 차이를 확인했어요.
3. 선택 순서를 revision과 statement 의미로 분리했습니다.
4. 중복과 정정 조건을 회귀 fixture에 추가했습니다.
5. 실제 PostgreSQL 조회 경로와 API 응답을 다시 확인했습니다.

## 결과를 확인한 방법

| 검증 대상 | 확인 방식 |
|---|---|
| 원천 보존 | content hash와 manifest 검증 |
| 정정공시 | 기존 행 덮어쓰기 대신 revision 추가 |
| 대표값 선택 | 중복 행과 정정 조건의 회귀 테스트 |
| 답변 기준 | 회사, 기간, 보고서, CFS 또는 OFS 검증 |
| 공시 문맥 | 검색 결과를 원문 위치와 evidence ID에 연결 |
| 실패 의미 | 근거 부족과 시스템 장애를 별도 상태로 유지 |
| 공개 안전성 | 실제 .env, API 키, 원문 snapshot 제외 검사 |

테스트 통과 수 자체를 성과로 내세우지 않습니다. 면접에서 중요한 근거는 실패 사례가 어떤 불변식을 깨뜨렸고, 수정 후 어떤 회귀 테스트로 그 불변식을 고정했는지입니다.

## 입증하지 않은 것

- 범용 GPT와 같은 PDF를 사용한 사용자 비교 우위
- 실제 사용자 이해도와 의사결정 개선
- 대규모 트래픽과 고가용성
- 응답시간이나 비용의 성능 개선
- 연속 공시 갱신의 장기 운영
- 모델 구성의 A/B 비교

이 항목은 향후 실험 후보이며 현재 성과가 아닙니다.
